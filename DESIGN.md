# Записка о дизайне среды (`DESIGN.md`)

Документ описывает архитектуру воспроизводимого симулятора финансового аудита `finaudit-rl-env`, устройство каузального генератора компаний и ошибок, механизмы процессной изоляции RL-среды, алгоритм взаимно однозначного сопоставления (`matcher`), анализ устойчивости функции награды, измеренный разбор сбоев базовых политик и честные ограничения системы.

---

## 1. Архитектура и поток данных

Симулятор спроектирован по принципу строгого разделения **открытого контура агента** и **закрытого контура оценщика**:

```text
[Seed + PolicyConfig]
        │
        ▼
┌───────────────────────────────────────────────────────────┐
│ 1. Каузальный генератор (generator/)                      │
│   ├─ company.py  -> Чистая сбалансированная книга (Дт=Кт) │
│   │                 + Distractors (split, recurring, ref) │
│   ├─ errors.py   -> Причинная инъекция 4+2 типов ошибок   │
│   ├─ transforms.py -> Перестановка строк и биекция ID     │
│   └─ verifier.py -> Независимая проверка баланса и улик   │
└───────────────┬───────────────────────────────┬───────────┘
                │ Открытые файлы (Read-Only)    │ Закрытые файлы
                ▼                               ▼
┌───────────────────────────────┐ ┌─────────────────────────┐
│ manifest.json, policy.json    │ │ truth.json              │
│ ledger.csv, invoices.jsonl    │ │ provenance.json         │
│ payments.jsonl, fx.csv        │ │ (Только в процессе      │
│ (EpisodeDataStore, limit<=50) │ │  EvaluatorServer)       │
└───────────────┬───────────────┘ └─────────────┬───────────┘
                │                               │
                ▼                               ▼
┌───────────────────────────────────────────────────────────┐
│ 2. Изолированная RL-среда (env/core.py + evaluator_server)│
│   reset(seed, config) -> (obs, info)                      │
│   step(action)        -> (obs, reward, term, trunc, info) │
│   Инструменты: list_records, get_record, get_document,    │
│                calculator (AST Decimal), submit           │
└───────────────────────────────┬───────────────────────────┘
                                │
                                ▼
┌───────────────────────────────────────────────────────────┐
│ 3. Оценщик и Матчер (scoring/matcher.py + reward.py)      │
│   ├─ Канонизация ID + проверка типа, валюты, допуска, улик│
│   ├─ Детерминированный 1-to-1 двудольный матчинг (Кун)    │
│   └─ Терминальная награда: clip(2*F1 - 1 - 0.002*steps)   │
└───────────────────────────────────────────────────────────┘
```

## 2. Каузальная генерация компании, ошибок и отвлекающих случаев (`generator/`)

### 2.1. Скрытая чистая история и бухгалтерские равенства
Генерация каждого эпизода (`company.py`, `fx_utils.py`) начинается с построения **100% чистой компании** за один отчётный период:
- Все денежные суммы хранятся исключительно в **целых минимальных единицах валюты** (`*_minor: int`) с явной картой разрядностей `currency_exponents` (`USD: 2`, `EUR: 2`, `GBP: 2`, `KZT: 2`, `CHF: 2`, `JPY: 0`).
- Все валютные курсы в `fx.csv` хранятся как точные десятичные строки (`Decimal`) и применяются строго по правилу `policy.fx_rate_date_rule` (`transaction_date`, `invoice_issue_date` или `previous_business_day`) и режиму округления `rounding_mode` (`HALF_EVEN` или `HALF_UP`).
- Каждая хозяйственная операция записывается двойной проводкой в `ledger.csv` (дебет счёта равен кредиту корреспондирующего счёта в базовой валюте компании `base_currency`). До инъекции ошибок выполняется строгий инвариант пробного баланса:
  $$\sum \text{debit\_minor} = \sum \text{credit\_minor}$$

### 2.2. Правдоподобные чистые отвлекающие случаи (`Distractors`)
Чтобы агент не мог получить высокую награду простыми эвристиками («пометить любой частичный платёж» или «пометить одинаковые суммы»), в чистую историю встраиваются 3 типа законных отвлекающих операций:
1. **Законные разбитые платежи (`split_payment`)**: один счёт оплачивается двумя легальными траншами (`part1 + part2 == total_minor`), где каждая проводка в `ledger.csv` в точности равна сумме соответствующего платёжного документа.
2. **Законные повторяющиеся суммы (`recurring_legitimate`)**: регулярные счета одному контрагенту на одинаковую сумму в разные расчётные циклы (`Billing Cycle 1`, `Billing Cycle 2` с интервалом $\ge 14$ дней).
3. **Законные урегулирования / возвраты (`refund_reimbursement`)**: полностью оплаченные и корректно закрытые в главной книге операции.

### 2.3. Четыре базовых типа ошибок и два сценария взаимодействия (`errors.py`)
Поверх чистой книги причинно вносятся ошибки (с записью состояния `before_state` / `after_state` в `provenance.json` и эталона в `truth.json`):
1. `duplicate_invoice`: повторное выставление и проведение в главной книге дубликата счёта с теми же товарными позициями и суммой, создающее лишнее начисление дебиторской задолженности и выручки.
2. `unallocated_or_partial_payment`: платёж поступил полностью в `payments.jsonl`, но в проводке погашения `ledger.csv` отражено только ~60% суммы (остаток не распределён).
3. `fx_conversion_error`: счёт в иностранной валюте пересчитан в `base_currency` по искажённому курсу (+15% к эталонному курсу из `fx.csv` по `policy.json`).
4. `period_cutoff_error`: счёт и его проводка фактически совершены за пределами отчётного периода `[period_start, period_end]` (с учётом часового пояса), но включены в книгу текущего периода.

**Два сценария взаимодействующих ошибок**:
- `partial_fx_cutoff`: счёт в иностранной валюте на границе отчётного периода одновременно содержит ошибку валютного пересчёта (`fx_conversion_error`) и частичное нераспределение платежа (`unallocated_or_partial_payment`).
- `duplicate_fx_cutoff`: счёт в иностранной валюте продублирован через границу отчётного периода (`duplicate_invoice` + `period_cutoff_error`).

Каждый сгенерированный эпизод проходит независимую проверку в `verifier.py`, которая подтверждает существование всех `affected_ids` и достаточность каждого набора доказательств из `valid_evidence_sets` только по открытым записям.

## 3. Контракт RL-среды и процессная изоляция (`env/`)

- **Контракт Gymnasium**:
  - `reset(seed, config) -> (observation, info)` изолирует состояние эпизода, сбрасывает бюджет (100 шагов) и таймер (60 секунд).
  - `step(action) -> (observation, reward, terminated, truncated, info)` принимает 5 действий: `list_records(table, cursor, limit<=50)`, `get_record(table, id)`, `get_document(doc_id)`, `calculator(expression)` и `submit(submission)`.
- **Безопасный AST-калькулятор (`calculator.py`)**: разбирает выражение через `ast.parse(..., mode="eval")`, разрешая только `Decimal`-числа и базовую арифметику (`+`, `-`, `*`, `/`, скобки, унарные знаки) с лимитом длины 500 символов и глубины AST 32.
- **Процессная изоляция (`evaluator_server.py` + `isolated_client.py`)**:
  - Оценщик и закрытые файлы (`truth.json`, `provenance.json`) работают в отдельном дочернем процессе `EvaluatorServer`, а агент взаимодействует через `IsolatedFinAuditEnv` по JSON-RPC (`stdin/stdout`). В адресном пространстве агента закрытых данных нет.
- **Разделение режимов `train` и `eval`**:
  - Во время исследования награда на каждом шаге равна `0.0`.
  - В открытом режиме `mode="train"` терминальная награда возвращается агенту на шаге `submit`.
  - В закрытом режиме `mode="eval"` награда и диагностика остаются только внутри оценщика до конца прогона.
- **Защита от утечек (`leak_checker.py`)**: автоматически проверяет все `observation`, `info`, ошибки и `artifacts/trajectories.jsonl` на отсутствие маркеров эталона (`truth.json`, `ISS-`, `expected_amount_minor`, `seed`) и путей файловой системы.

## 4. Сопоставление выводов (`matcher.py`) и функция награды (`reward.py`)

### 4.1. Правила нормализации и 1-to-1 матчинга
Вывод агента `Finding` сопоставляется с эталонной ошибкой `TruthIssue`, если одновременно выполнены все 5 условий:
1. Совпадает тип ошибки `finding.type == truth_issue.type`.
2. Каноническое множество затронутых записей совпадает точно: `normalize_ids(finding.affected_ids) == normalize_ids(truth_issue.affected_ids)`.
3. Совпадает валюта `finding.currency == truth_issue.currency`.
4. Сумма расхождения находится в пределах допуска: `|claimed_amount_minor - expected_amount_minor| <= tolerance_minor`.
5. Множество `normalize_ids(finding.evidence_ids)` является надмножеством хотя бы одного полного набора доказательств из `truth_issue.valid_evidence_sets`.

Для исключения неоднозначности используется **детерминированный алгоритм максимального двудольного паросочетания (алгоритм Куна)** с приоритетом по минимальному расхождению суммы и каноническому `issue_id`. Каждая эталонная ошибка может быть сопоставлена максимум с одним выводом агента (`1-to-1`). Все повторные выводы (дубли) и несопоставленные выводы попадают в `FP`, а пропущенные ошибки — в `FN`.

### 4.2. Метрики и терминальная награда
- $P = \frac{TP}{TP + FP}$, $R = \frac{TP}{TP + FN}$, $F_1 = \frac{2 \cdot TP}{2 \cdot TP + FP + FN}$.
- На чистых компаниях (`truth.issues == []`): если выводы пусты (`findings == []`), то $P = R = F_1 = 1.0$; если агент отправил хотя бы одно ложное обвинение (`FP > 0`), то $F_1 = 0.0$.
- Терминальная награда:
  $$\text{Reward} = \text{clip}\left(2 \cdot F_1 - 1 - 0.002 \cdot \text{inspection\_steps},\ -1.0,\ 1.0\right)$$
- Любое нарушение схемы или лимитов (`>30` выводов, `>10` ID доказательств, `>1000` символов объяснения, неверный `episode_id`) немедленно завершает эпизод с наградой `-1.0`.

### 5.2. Измеренный разбор сбоев (`Failure Analysis`)
1. **Почему `simple_reconciler` получает `F1 = 0.9768` вместо `1.0000` (`5 FP` и `2 FN` на 20 эпизодах / 76 ошибках)?**
   - В эпизодах со сложными взаимодействующими ошибками (`ep_train_007`, `ep_train_010`, `ep_dev_007`, `ep_dev_010`) возникает каузальное наложение: когда счёт в иностранной валюте сдвигается за границу отчётного периода (`period_cutoff_error`, например на `2026-08-03`), его проводка в главной книге остаётся посчитанной по курсу исходной даты внутри периода.
   - Пошаговая эвристика `simple_reconciler` проверяет правила независимо: она верно находит `period_cutoff_error`, но затем берёт курс `fx.csv` на новую (сдвинутую) дату `2026-08-03`, видит расхождение с суммой проводки и выдвигает лишнее обвинение `fx_conversion_error` (`FP`).
   - Аналогично, в сценарии `partial_fx_cutoff` (`ep_train_010`, `ep_dev_010`), где на одном инвойсе одновременно искажён курс начисления и частично распределён платёж, линейный сверщик допускает 1 пропуск (`FN`) на пересечении валютной разницы и недоплаты.
   - Это подтверждает главное требование ТЗ: **среда не решается тривиальным набором независимых `if/else`-правил на 100% — для достижения уровня `Oracle` (`+0.9984`) агенту необходимо рассуждать о причинной истории документа**.
2. **Провал атаки `flag_all_attack` (`Mean Reward = -1.0000`)**:
   - Спам из 30 выводов без точного совпадения полного канонического множества `affected_ids` и `valid_evidence_sets` даёт `600 FP` на 20 эпизодах и минимально возможную награду `-1.0000`.

### 5.3. Честные ограничения системы
1. **Модель плана счетов**: главная книга использует фиксированный синтетический план счетов (`1100_Accounts_Receivable`, `4000_Sales_Revenue`, `1000_Cash_and_Bank` и 5 операционных счетов OpEx) и не моделирует многоуровневую налоговую отчётность (НДС/VAT, отложенные налоги) или консолидацию дочерних обществ.
2. **Валютные пары**: таблица `fx.csv` содержит прямые кросс-курсы к базовой валюте компании (`source_currency -> base_currency`) без необходимости выстраивать триангуляцию через третью валюту.
3. **Назначение**: среда предназначена для исследовательского RL-обучения и бенчмаркинга алгоритмов инструментального расследования, а высокая награда в симуляторе не заменяет сертифицированное аудиторское заключение по МСА (ISA).
